# 機能開発プロトコル

この文書は、新機能や修正を既存の軽量DDDコンテキストとプロダクト根拠に沿って実装するための短い運用手順である。必須のDoDゲートは [DEFINITION_OF_DONE.md](DEFINITION_OF_DONE.md) を優先する。

## 実装前の最小チェック

1. `REQUIREMENTS.md` で対象のFR/NFRを特定する。存在しない要求なら、先に要件を追加またはユーザーに確認する。
2. `PRD.md` でプレイヤー体験、データ、ゲームループへの影響を確認する。
3. `PLAN.md` で既存フェーズとの整合を確認する。
4. [ARCHITECTURE.md](ARCHITECTURE.md) のコンテキストマップを使い、機能の所有者を一つ決める。
5. [TASK_TEMPLATE.md](TASK_TEMPLATE.md) に、範囲・非範囲・リスク・FR・観測可能なDoD・検証を記録する。

## 実装ルール

- ルールと不変条件は `features/<context>/domain` に置く。
- 一つ以上の画面・入力経路を調整する操作は `application` に置く。不要な場合は追加しない。
- ブラウザ、HTTP、保存、圧縮、Web Audioは `infrastructure` に閉じ込める。
- React、Canvas、モーダル、アクセシビリティ表示は `presentation` に置く。
- 他コンテキストや `app` が使うものだけを `features/<context>/index.ts` から公開する。
- 共有カーネルは安定した語彙に限る。機能固有の判断ロジックを置かない。

## 要件別の追加確認

| 変更の種類 | 必須の追加確認 |
| --- | --- |
| 生態系・遺伝 | 極端値、停止状態、上限、不変条件、乱数の再現方法 |
| UI | キーボード、表示名/状態、320px相当の小画面、空・エラー状態 |
| DNA・保存・共有 | 新旧の往復、破損入力、上限、復元失敗がアプリ全体を停止しないこと |
| Audio | ユーザー操作後の初期化、ミュート、非対応ブラウザでの安全な失敗 |
| Canvas | 長時間更新、上限個体数、リソース解放、タッチ入力 |

## PRレビューの出口条件

- 要件IDとDoDが対応している。
- 変更は一つのコンテキストが所有し、境界を越える依存は公開API経由である。
- ドメインルールのテストと、影響した公開契約のテストがある。
- `pnpm test`、`pnpm build`、必要な手動確認の証拠がある。
- `ARCHITECTURE.md`、PRD、要件、コードに矛盾がない。
